# ProfileService — персональные настройки

Сохраняет направление, уровень, регионы и изученные навыки в PostgreSQL.
Структура: `Api`, `Application`, `Domain`, `Infrastructure`. В Docker запускается
API вместе с подключёнными библиотеками.

## Запуск

Из корня репозитория:

```sh
docker compose up -d --build
```

- Профиль на сайте: http://127.0.0.1:8080/#/profile
- Swagger: http://127.0.0.1:8080/api/profile/swagger/index.html
- OpenAPI: http://127.0.0.1:8080/api/profile/openapi/v1.json
- Aspire: http://127.0.0.1:18888

Swagger доступен в Development. Нажмите **Authorize**, вставьте `accessToken`
из ответа `POST /api/auth/login`, затем выполняйте запросы своего профиля.
OpenAPI указывает сервер `/api`: вызовы проходят через Gateway. Авторизация
Swagger не сохраняется между перезагрузками.

## API

| Метод | Путь через Gateway | Назначение |
| --- | --- | --- |
| GET | `/api/profile/me` | Получить свой профиль |
| PUT | `/api/profile/me` | Сохранить настройки с проверкой версии |
| DELETE | `/api/profile/me` | Сбросить свой профиль |
| GET | `/api/profile/catalog` | Получить текущие допустимые значения |

Все методы требуют `Authorization: Bearer <accessToken>`. ID пользователя берётся
из проверенной сессии; поля `userId`, email и неизвестные поля в PUT не принимаются.

```json
{
  "direction": "analyst",
  "level": "junior",
  "regions": ["Москва", "Удалённая работа"],
  "skills": ["Анализ требований", "SQL"],
  "version": 0
}
```

Ответ также содержит `userId`, новую `version` и `updatedAt`. Первый GET возвращает
настройки по умолчанию с версией 0, без создания строки в БД. Первый PUT с версией 0
создаёт профиль версии 1; следующие передают полученную версию. Устаревшая версия
возвращает `409`, сохраняя актуальные данные. DELETE возвращает `204`, следующий
GET — настройки по умолчанию версии 0. Некорректный запрос — `400`.

ProfileService проверяет Bearer через `/auth/me` Auth Service на каждом запросе,
включая подпись JWT, срок действия и отзыв сессии. Выход и удаление аккаунта
немедленно закрывают доступ (`401`). При недоступном Auth возвращается `503`.
Приватный ключ подписи и таблицы Auth для этого не используются.

Направления: `analyst`, `csharp`, `qa`; уровни: `all`, `intern`, `junior`, `middle`,
`senior`. Пустые регионы означают всю Россию, повторы удаляются. Навыки других
направлений сохраняются при переключении цели. Навыки проверяются по текущему
справочнику SkillService (`Skills__Address`), включая JSON-импорт администратора.
Если SkillService недоступен, PUT возвращает `503` без изменения настроек.
Уровни и регионы пока заданы локально; интеграция ID из справочников — следующий
этап. Вакансии остаются демонстрационными; личный roadmap рассчитывает RecommendationService.

## БД и миграции

Compose использует существующий `auth-db`, БД `skill_day_auth` и отдельную схему
`profile`. Настройки: `ConnectionStrings__ProfileDb`, `Database__Password`.
Общий пользователь PostgreSQL — настройка локального окружения.

FluentMigrator применяет миграции только ProfileService, история — `VersionInfo`.
EF-миграции Auth независимы. Старая числовая схема профиля преобразуется в UUID
из Auth Service. Если в старых таблицах есть записи, миграция останавливается:
требуется явное сопоставление старых ID и UUID, без удаления существующих данных.

В локальном Compose включён `Profile__AutoMigrate=true`. Для сервера задайте
подключения, `Auth__Address`, собственный `Internal__Key`, примените миграции
одним процессом `dotnet ProfileService.Api.dll --migrate`, затем запускайте API с
`Profile__AutoMigrate=false`. Общий `backend/Migrator` в этом Compose не запускается.

## Удаление аккаунта

Auth записывает задачу `AccountDeletion` в одной транзакции с удалением аккаунта.
Worker вызывает внутренний DELETE `/internal/profiles/{userId}`, повторяя доставку
при сбое без конечного лимита попыток. Завершённые задачи очищаются через 7 дней.
Удалённый пользователь уже не имеет доступа, пока очистка ожидает доставки.

Внутренний маршрут отсутствует в Gateway и требует `X-Service-Key`. В Compose
общий ключ задаётся `PROFILE_SERVICE_KEY`; в сервисах — `Internal__Key` и
`ProfileCleanup__Key`. Значение `local-development-only` допустимо в Development;
ProfileService отклоняет его в Production. При отдельном запуске Auth доставка
может оставаться выключенной до настройки `ProfileCleanup__Address`.

Навыки и регионы удаляются каскадно. В `profile.deleted_accounts` остаётся
техническая UUID-отметка без настроек: она предотвращает повторное создание
профиля запросом, начатым до удаления аккаунта. Очистка и сохранение сериализуются
по пользователю. Новая регистрация с тем же email имеет другой UUID.

## Фронтенд и проверки

Настройки загружаются с сервера. Сохранение подтверждается после ответа API;
при сбое показывается ошибка, при `409` можно явно загрузить актуальный профиль.
Данные восстанавливаются при входе с другого устройства.

Старый ключ `skill-day-profile:<userId>` импортируется только для своего аккаунта
при серверной версии 0 и удаляется после успеха. Сохранённые серверные настройки
имеют приоритет; общий старый ключ и данные других пользователей не импортируются.

```sh
node --test backend/Services/ProfileService/tests/profile.test.mjs
```

Проверяются реальная БД, сессии, изоляция пользователей, валидация, параллельные
записи, удаление, Swagger и трассировка Gateway → Profile → Auth. Для проверки
удаления используется локальный `docker compose exec auth-db`.

```sh
cd frontend
PROFILE_INTEGRATION=1 PLAYWRIGHT_BASE_URL=http://127.0.0.1:8080 npm run test:e2e -- --grep 'Real ProfileService'
```

Браузерные тесты используют независимые контексты для двух устройств. Тестовые
аккаунты создаются и удаляются автоматически. Полные Auth API и Profile API тесты
запускайте в разных минутных окнах: в локальном окружении у них общие IP-лимиты.
