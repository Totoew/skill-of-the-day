# RecommendationService — персональный roadmap

Считает охват, слои дефицита, базовые навыки, последовательность шагов,
индивидуальный вклад навыка, прирост охвата в процентных пунктах и вакансии-основания.
Личный кабинет использует результат API для графа, таблицы и карточки навыка.
Расчёт в браузерном Web Worker удалён.

Четыре проекта: Domain (алгоритм и модели), Application (сценарий расчёта),
Infrastructure (HTTP-клиенты и источник вакансий), Api (маршруты и доступ).
Сервис не хранит состояние и не требует отдельной БД. Каждый ответ содержит
версии профиля и справочника, ID и дату среза для объяснения результата.

## Запуск

Из корня репозитория:

```sh
docker compose up -d --build
```

- Личный кабинет: http://127.0.0.1:8080/#/plan
- Swagger: http://127.0.0.1:8080/api/recommendations/swagger/index.html
- OpenAPI: http://127.0.0.1:8080/api/recommendations/openapi/v1.json
- Aspire: http://127.0.0.1:18888

Swagger доступен в Development. В Authorize передайте `accessToken` из входа.
Документ использует сервер `/api`, поэтому Try it out проходит через Gateway.
Авторизация Swagger не сохраняется между перезагрузками.

## Что сейчас настоящее, а что демонстрационное

Профиль загружается из ProfileService, справочник и базовые навыки — из
SkillService. Сам расчёт выполняет настоящий API RecommendationService.

**Вакансии в локальном Compose остаются демонстрационными.**
`Vacancies__Provider=Demo` использует встроенный синтетический срез от 20.10.2026:
120 вакансий на каждое из трёх направлений. Это проверочный набор с готовыми
требованиями, без текстового разбора и реальных внешних ссылок. Поле ответа
`source: "demo"` и надпись в интерфейсе показывают происхождение данных.
В качестве справочника используется текущий серверный каталог; демовакансии
не изменяются вслед за импортом. Новый базовый навык виден в плане, но его
импорт не создаёт вакансии и не увеличивает охват.

Текущий VacancyService ещё не публикует распознанные требования и контракт
среза ниже. Поэтому подключение к реальным вакансиям **ещё не выполнено**.
Адаптер HTTP подготовлен и проверен на контрактных тестах; он не обращается
к старому `/api/v1/vacancies`, где отсутствуют нужные требования.

Публичная статистика и демонстрационные действия накопителя администратора
пока остаются во фронтенде. Их данные не являются источником личного плана.

## API

| Метод | Путь через Gateway | Назначение |
| --- | --- | --- |
| GET | `/api/recommendations/plan` | Рассчитать план своего сохранённого профиля |
| POST | `/api/recommendations/recalculate` | Повторить расчёт по текущим данным |

Оба метода требуют действующей Bearer-сессии. Параметры query:

- `profileVersion` — ожидаемая версия профиля, необязательная; сайт передаёт её всегда.
- `layer` — необязательный слой, целое число 0–256. Без параметра выбран весь срез.
  Если такого слоя в актуальном профиле больше нет, API возвращает весь срез
  с `selectedLayer: null`.

Пример: `GET /api/recommendations/plan?profileVersion=3&layer=2`.
Тело запросов не принимается; нельзя передать чужой `userId`, изученные навыки
или собственные вакансии. Неизвестные и повторные query-параметры отклоняются.

Результат содержит:

- `profileVersion`, `catalogVersion`, `source`, `snapshotId`, `snapshotDate`;
- `scopeCount` — размер всего допустимого среза; `total` — вакансий в выбранном слое;
- `layers`, `selectedLayer`, `covered`, `minimumDeficit`;
- `basicSkills`, `remainingBasics`, `noSkills`, `basics` с показателями навыков;
- `steps` с последовательными шагами и индивидуальными `metrics`;
- `jobs` — ID, название, безопасная ссылка и обязательные навыки вакансий;
- `excludedVacancies` — исключённые в выбранной географии и уровне вакансии.

Метрика навыка: `skill`, `category`, `before`, `after`, `gain`, `points`, `basisIds`.
`gain` всегда равен длине `basisIds` и разности `after - before`.
`points = gain / total * 100`, для пустого среза — 0.
Описание вакансии, цитаты требований, работодатель и условия не передаются.

Ошибки: `400` — параметры, `401` — отсутствующая/отозванная сессия,
`409` — изменилась версия профиля, `503` — недоступны или некорректны исходные
данные, `504` — превышено время расчёта. При сбое источник не заменяется
пустым или демонстрационным срезом. HTTP-ответы имеют `Cache-Control: no-store`.

## Алгоритм

1. Определяется пользователь по сессии. ProfileService получает его Bearer
   и возвращает только его профиль; UUID в ответе проверяется.
2. По направлению, уровню и объединению регионов выбираются вакансии.
   «Удалённая работа» включает remote-вакансии, пустой список регионов — всю Россию.
3. Коды, имена и синонимы требований нормализуются по SkillService. Точный код
   имеет приоритет; имена/синонимы сравниваются с Unicode NFKC без различия
   регистра и повторных пробелов. Повторные требования учитываются один раз.
4. Вакансии с нераспознанной структурой, неизвестным обязательным навыком либо
   пометкой исключения не входят в расчёт. Неизвестные необязательные требования
   пропускаются. Нельзя удалить неизвестный обязательный навык и считать вакансию доступной.
5. Слой — число недостающих обязательных навыков относительно текущего профиля.
   Выбор слоя меняет набор вакансий и знаменатель всех показателей плана.
6. Базовые навыки показываются до отметки изучения. Если пользователь ещё не
   изучил ни одного навыка направления, возвращается нулевой экран без roadmap.
7. Специализированные шаги прогнозируются после основ и предыдущих шагов:
   выбирается ближайший непустой дефицит, среди равных наборов — максимальный
   прирост охвата. При равенстве сохраняется порядок исходного среза.
8. На шаге до пяти связанных навыков. Для большего набора возможен частичный
   шаг с нулевым приростом, уменьшающий дефицит. Для отдельного навыка совместного
   шага учитываются остальные навыки шага; его вклад совпадает с его основаниями.

Лимита в три шага или четыре слоя нет; проверен план из 20 последовательных навыков.
Защитные пределы: до 10 000 вакансий во входном ответе, до 5000 в выбранном
направлении/географии/уровне и до 256 уникальных обязательных навыков среза,
до 64 требований каждого класса на вакансию. Удалённые ответы — до 16 МБ;
таймаут HTTP-клиентов 8 секунд, расчёта после проверки сессии — 20 секунд.
Эти пределы возвращают ошибку, не обрезают выдачу молча.

## Подключение настоящего источника вакансий

Настройки сервиса:

```text
Auth__Address=http://auth-service:8080/
Profile__Address=http://profile-service:8080/
Skills__Address=http://skill-service:8080/
Vacancies__Provider=Http
Vacancies__Address=http://vacancy-service:8080/
```

`Http` — значение по умолчанию вне Compose; `Demo` допускается только в
Development. Для `Http` обязателен адрес. Неудачный HTTP-запрос не переключает
сервис на Demo. Auth проверяет подпись, срок действия и отзыв сессии; ключ подписи
и таблицы других сервисов напрямую не читаются. Bearer передаётся только Auth
и ProfileService, не справочнику и источнику вакансий.

Источник должен реализовать:

```text
GET /vacancies/snapshots/latest?direction=analyst
```

Пример ответа контракта, **это ещё не существующий endpoint VacancyService**:

```json
{
  "schemaVersion": 1,
  "snapshotId": "analyst-2026-11-25",
  "collectedAt": "2026-11-25T08:00:00Z",
  "vacancies": [
    {
      "id": "hh-123456",
      "direction": "analyst",
      "title": "Системный аналитик",
      "level": "middle",
      "region": "Москва",
      "remote": false,
      "required": ["sql", "rest-api"],
      "desired": ["git"],
      "mentioned": [],
      "url": "https://hh.ru/vacancy/123456",
      "structureRecognized": true,
      "excluded": false
    }
  ]
}
```

ID вакансий в срезе уникальны. `required`, `desired`, `mentioned` — массивы
кодов SkillService; поддерживаются также канонические названия и синонимы.
Вакансия без обязательных навыков допустима только как распознанная структура;
сырая неразобранная вакансия должна иметь `structureRecognized: false`.
Уровни: intern/junior/middle/senior; направления пока analyst/csharp/qa.
Интервал срезов согласован в пять дней. Этот сервис не запускает сбор по расписанию
и не вычисляет исторические тренды; это ответственность будущего источника/аналитики.

## Интерфейс и трассировки

Дизайн графа, табов и фильтра слоёв сохранён. При пересчёте показывается состояние
обработки и предыдущий результат, элементы плана блокируются. Ошибки доступны
для повторной попытки; конфликт версии предлагает загрузить актуальный профиль.
При первой ошибке локальный расчёт не подставляется. Отменённые и устаревшие
запросы не перезаписывают новый результат.

В Aspire один TraceId связывает Gateway → Recommendation → Profile → Auth,
а также Recommendation → Skill. JSON с профилем, токены и тела запросов
в HTTP-журналы не пишутся. После подключения Http появится запрос к источнику вакансий.

## Проверки

```sh
dotnet build backend/Services/RecommendationService/RecommendationService.Api/RecommendationService.Api.csproj -c Release
node --test backend/Services/RecommendationService/tests/calculation.test.mjs
node --test backend/Services/RecommendationService/tests/api.test.mjs
cd frontend
RECOMMENDATION_INTEGRATION=1 PLAYWRIGHT_BASE_URL=http://127.0.0.1:8080 npm run test:e2e -- --grep 'Real RecommendationService'
```

Контрактные тесты запускают собранный API с изолированными HTTP-источниками;
сравнивают C# с прежним JS-алгоритмом на 45 сочетаниях направления, уровня и
регионов, включая каждый слой. Проверяются нулевой/пустой экран, совместные шаги,
20 навыков, нормализация, исключения, подмена пользователя и отказы зависимостей.
API-интеграция использует настоящий локальный Compose и временные аккаунты,
которые удаляются после теста. Браузер проверяет граф, таблицу, основания,
фильтрацию, ручной пересчёт и мобильный вид.
